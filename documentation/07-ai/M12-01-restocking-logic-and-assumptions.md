# M12-01 — Restocking Logic and Assumptions

## 1. Purpose

Define a transparent, configurable baseline for inventory reorder recommendations for each store-product combination. Recommendations support decisions; they do not create purchase orders automatically.

## 2. Data inputs

- Store ID and Product ID identify each inventory series.
- Date identifies the effective date of the inventory record and forecast.
- Inventory Level is the current on-hand quantity for that store and product.
- Forecast Units Sold is the prediction generated by the RetailAI forecasting model.
- Units Sold is historical observed demand and may be used as a fallback when an appropriate model forecast is unavailable.

Join forecasts and inventory by Store ID, Product ID and Date. Never mix different stores or products. Do not treat the dataset's supplied `Demand Forecast` field as a newly generated model prediction.

## 3. Baseline assumptions

| Setting | Initial value | Reason or limitation |
|---|---:|---|
| Supplier lead time | 3 days | Provisional default; replace when verified supplier data exists. |
| Review period | 1 day | Assumes stock is checked daily. |
| Safety-stock buffer | 1 day of forecast demand | Simple initial buffer, not a calibrated service level. |
| Demand unit | Units sold per store-product per day | Matches daily observations. |
| Order quantity | Whole units | Round required quantities upward. |
| Negative forecast | Treat as 0 | Demand cannot be negative. |
| Missing or invalid stock | Flag for data review | Never silently treat missing stock as zero. |
| Missing model forecast | Mean of available prior 7 days of observed demand | Use historical rows only; otherwise flag insufficient history. |

These are prototype defaults and must remain configurable. They are not verified supplier requirements.

## 4. Calculation rules

Let:
- `d` = non-negative daily demand forecast.
- `L` = supplier lead time in days, default 3.
- `R` = inventory review period in days, default 1.
- `S` = safety-stock days, default 1.
- `I` = current on-hand inventory.

Calculate:

- `safety_stock = ceil(d * S)`
- `reorder_point = ceil(d * L + safety_stock)`
- `target_stock = ceil(d * (L + R) + safety_stock)`
- If `I <= reorder_point`, `suggested_order_quantity = max(0, target_stock - I)`.
- Otherwise, `suggested_order_quantity = 0`.

Order quantities must be whole units. Minimum order quantities, pack sizes, storage limits and other constraints can be added when verified data becomes available.

## 5. Recommendation statuses

- `REORDER_NOW`: Valid stock and demand data exist, and stock is at or below the reorder point. Recommend the calculated quantity.
- `WATCH`: Stock is above the reorder point but below target stock. Flag for attention without automatically ordering.
- `HEALTHY`: Stock is at or above target stock. Suggested order quantity is zero.
- `DATA_REQUIRED`: Stock is missing, invalid or negative. Do not calculate an order quantity.
- `INSUFFICIENT_HISTORY`: Neither a suitable forecast nor enough prior observed demand is available. Do not guess a quantity.

A zero order quantity does not guarantee that an item cannot run out of stock.

## 6. Data quality and safety rules

1. Validate store ID, product ID, date, stock and forecast inputs.
2. Reject invalid or non-finite numerical values. Normalize negative forecasts to zero and flag negative inventory.
3. Use only information available as of the recommendation date. Never use future actual sales to produce a past recommendation.
4. Keep historical demand calculations separate for each store-product combination.
5. Make lead time, review period and safety-stock settings configurable.
6. Record the as-of date, input values, settings, status and recommendation reason.
7. Recommendations are advisory; a user must confirm an order before a real purchase is made.

## 7. Known limitations

The approved dataset does not provide verified supplier lead times, minimum order quantities, pack sizes, ordering calendars, budgets, storage limits or product shelf-life information. The baseline cannot reliably optimize these factors or claim expiry-aware ordering without additional data.

## 8. Planned output fields

The initial implementation should return one record per store-product and as-of date:

`Date`, `Store ID`, `Product ID`, `Inventory Level`, `Forecast Daily Demand`, `Lead Time Days`, `Safety Stock`, `Reorder Point`, `Target Stock`, `Suggested Order Quantity`, `Recommendation Status`, `Reason`.

Example reason: `Stock 8 is at/below reorder point 12; recommended order quantity is 8 to reach target stock 16.`

## 9. Verification scenarios for M12-02 and M12-05

| Scenario | Expected result |
|---|---|
| Stock is above reorder point | No order; WATCH or HEALTHY depending on target stock. |
| Stock equals reorder point | REORDER_NOW; order up to target stock. |
| Stock is below reorder point | REORDER_NOW; positive quantity to reach target stock. |
| Forecast is negative | Use zero demand and record the normalized input. |
| Stock is missing or invalid | DATA_REQUIRED; no numeric order recommendation. |
| Forecast is missing but prior demand exists | Use the mean of available prior 7-day demand, never future rows. |
| Forecast and prior demand are unavailable | INSUFFICIENT_HISTORY; no guessed quantity. |
| The same product appears in two stores | Calculate each store-product independently. |

## 10. Dependencies and scope

- M11-05 provides temporal holdout evaluation evidence.
- M11-06 provides model-generated rolling one-step-ahead forecast outputs, not a fixed future forecast without new observations.
- M12-01 defines assumptions and decision rules.
- M12-02 implements reorder recommendations.
- M12-03 implements stockout detection.
- M12-05 validates restocking scenarios.
